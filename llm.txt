Engram LLM Guide

Purpose

Engram is a portable, human-approved memory layer for AI agents. It stores
durable rules, workflows, skills, and knowledge as Markdown files, then routes
only the relevant memory for the current task.

Treat Engram as the knowledge memory center for project, workspace, team, and
personal context.

Core operating model

- Workspace memory is preferred first.
- Global memory is fallback for cross-repo personal or team context.
- Read commands are compact by default.
- Write commands require human-visible approval unless the human explicitly
  requested a force path for that command.
- Markdown memory files are the source of truth. Indexes, graphs, and optional
  vector sidecars are acceleration layers (the hashed vector sidecar is
  experimental and off by default for new configs).
- For runtime-capable hosts, Engram installs small bootstrap instructions
  instead of the full protocol; MCP tools and Agent Skills carry the detail.
  Fallback targets get compact manual instructions.
- The SQLite config DB is optional. If it cannot be opened or initialized,
  commands fall back to JSON config snapshots.

What AI agents should do first

If Engram hooks are installed (`engram link <host>`), context is injected
automatically at session start, on later prompts, in subagents, and when files
that match a memory's `applies_to` globs are touched; do not run `engram load`
just to start a session. Without hooks, at the start of a task
run:

engram load "<current task>"

Default reply shape:

Engram loaded: X memories / Y total related memories.

Do not paste large memory blocks into chat unless the human explicitly asked for
raw output, file IDs, or exact rule text.

When to load again

Run `engram load` again when:

- the task changes materially
- the human switches domain or scope
- you changed active roles or rule-variant mode
- research or implementation depends on project knowledge that may not already
  be in the current compact memory pack

If `engram set-role ...` or `engram set-rule-variant ...` returns `Agent action:`
then rerun:

engram load "<current task/request>"

That reload replaces earlier Engram-derived context in the current conversation.

Read path

Primary read commands:

- `engram load "<task>"`: route relevant memory for the current task and render compact AI-agent output
- `engram load --id <id,...>`: fetch the full body of memories shown as one-line cards
- `engram load --budget-tokens <n> "<task>"`: hard-cap the complete compact output (200-16000)
- `engram load --disclosure full "<task>"`: print every packed body instead of the tiered pack
- `engram load --dry-run "<task>"`: preview routed files, candidate counts, and
  narrowing tags without printing memory contents
- `engram load --all "<task>"`: bypass the compact load cap only when broad
  context is explicitly requested
- `engram search "<query>"`: search visible memory
- `engram route "<task>"`: classify a task into the stable task type used by
  routing and save tags
- `engram graph "<query>"`: inspect dependency layers and contradiction hints
- `engram verify`: verify memory hashes before trusting files
- `engram repair`: report malformed memory files
- `engram entry`: show active roots, profile, and runtime configuration
- `engram stats`, `engram health`, `engram quality-check`: inspect memory health
- `engram stats --usage`: show which memories agents fetch and which are injected but never fetched
- `engram verify --sources`: re-hash the source files of take-control memories and record stale ones

How routing works

Default `engram load` is tiered. The top `load.expand_top` hits (default 3) are
printed as bodies under `### <id> [<type>, <authority>]` (plus `requires: <ids>`
when the memory has `depends_on`). Every other selected hit, plus up to 5
omitted candidates, is one card line, `- <id> [<type>] <directive-or-summary>`
(` (stale)` is appended when its sources changed), under `related:`. The output
ends with `fetch: engram load --id <ids>`; run it only for cards you need.
Frontmatter, `## Context`, `## Example`, and `## Origin` are not rendered for
agents. For rules, one selected variant is rendered.
`load.disclosure: full`, `--disclosure full`, `--full`, and `--all` skip tiering.

`engram load` does not blindly load all memory. It:

1. Anchors on meaningful query terms.
2. Ranks candidates with BM25 over id, tags, `directive`, summary, triggers, and
   content terms (light stemming), then scales by lifecycle (`review_due`),
   staleness, confidence, and scope, with a small boost for memories agents
   fetch. Expired `valid_until` memories are left out (reason `lifecycle`).
   A query with 4 or more anchors needs 2 anchor hits or one hit on a strong
   field (id, tag, directive, `applies_to` path). Vector hits alone never admit a
   memory.
3. Refines results to a compact context pack within the token budget.
4. Reports selected memory count and total related matches.

If memory files declare `depends_on: [...]`, routed prerequisites are kept before
deeper dependent memories in the compact load pack.

`workflow` queries may route to skill memories. Generic words such as `rule`,
`knowledge`, or common stopwords should not by themselves trigger broad matches.

Read behavior and proof

Hook-capable hosts can use:

- `engram set-read startup`
- `engram set-read auto`
- `engram set-read always`
- `engram set-read manual`
- `engram set-read off`

Meaning:

- `startup`: inject only at session start
- `auto`: inject at session start and later turns, delivering only memory bodies not yet delivered in this session (`already loaded: <ids>` marks the rest)
- `always`: inject on every eligible prompt
- `manual`: disable automatic hook reads but keep manual `engram load`
- `off`: suppress automatic read surfaces

Diagnostics, review, and safe automation

- `engram doctor --strict --json`: run deterministic CI diagnostics; strict mode fails on warnings or failures.
- `engram load --explain --json "<task>"`: expose selected IDs, ranking evidence, dependencies, and omissions without memory bodies.
- `engram review list|inspect|dismiss|verify|supersede|archive`: inspect and approve lifecycle findings; actions remain human-controlled.
- `engram benchmark <cases.json> --json --fail-on forbidden,recall`: run versioned retrieval regression cases; reports contain IDs and metrics only.
- `engram policy init|show|validate|rollback`: manage the local deny-by-default team policy and audit rollback receipts.
- `engram autosave --policy --dry-run "TYPE: knowledge | TEXT: ..."`: preview policy-gated automation. Autonomous writes require an explicit reviewed policy and quota.
- `engram capabilities --json`: inspect host-specific instruction, MCP, hook, proof, and transcript capabilities.

Transcript capture is disabled by default. An explicit `.agents/engram.transcripts.json`
with `enabled: true` may allow supported hooks to create sanitized, non-indexed
inbox observations; transcript events never become active memories automatically.

Hook events per host:

- Codex: `SessionStart`, `UserPromptSubmit`, `PreToolUse` (`apply_patch` edits),
  `PreCompact`, `SubagentStart`.
- Claude: `SessionStart`, `UserPromptSubmit`, `InstructionsLoaded`, `PreCompact`,
  `SubagentStart`. With `hooks.path_rules hook`, `PreToolUse`
  (`Read|Edit|Write|MultiEdit`) replaces `InstructionsLoaded`.
- Gemini: `SessionStart`, `BeforeAgent`, `AfterTool` (`read_file|write_file|replace`),
  `PreCompress`.

Memories with `applies_to` globs reach Claude and Cursor as generated native rule
files (`.claude/rules/engram/<id>.md`, `.cursor/rules/engram/<id>.mdc`; working-tier
memories are never written there). The Claude `InstructionsLoaded` hook only records
that a rule file loaded, so the body is not injected twice. Where a hook injects a
path match (Codex `PreToolUse`, Gemini `AfterTool`, Claude in hook mode) it adds up
to 3 undelivered memories and never blocks the tool. `SubagentStart` (Claude, Codex)
injects the routed context into each subagent with its own delivered set.
`SessionStart` and `PreCompact` (Gemini: `PreCompress`) reset the delivered set.
Hook output stays under host caps: 2,400 tokens on Codex, 9,500 characters on
Claude, `load.max_tokens` elsewhere; over the cap, bodies become cards.
`engram upgrade --latest` (or re-running `engram link <host>`) adds the new events
to an older install.

Proof visibility is separate:

- `engram set-proof off`
- `engram set-proof compact`

With `compact`, supported hooks (codex, claude, gemini, opencode, cursor,
windsurf) may append a short `Engram proof:` line showing whether memory was
loaded, reused, or skipped.

Write path and approval

Never write durable memory silently; working-tier notes are gitignored, expire, and are redacted.

Write and proposal commands:

- `engram save rule "<text>"`
- `engram save knowledge "<text>"`
- `engram save skill "<text>"`
- `engram save workflow "<text>"`
- `engram save-session`
- `engram save-session --file transcript.md`
- `engram observe "note"`
- `engram take-control --plan`
- `engram take-control --all`
- `engram take-control --from claude-auto-memory|codex-memories --plan`
- `engram metacognize --workspace|--global|--all`
- `engram clone-memory ... --metacognize`
- `engram archive --reason "<why>" <id-or-file>`
- `engram resolve-conflicts --metacognize`
- `engram working note "<text>"` (one yes/cancel approval; working tier only)

How to choose memory type

- Rule: a durable instruction, correction, or preference agents must follow
- Knowledge: an objective project fact or stable context
- Skill: a repeatable capability or habit
- Workflow: a repeatable multi-step procedure

Save behavior

`engram save` proposes one memory. Engram may automatically choose update-vs-new
before showing the approval preview.

Every candidate preview carries one `Verdict:` line: `ADD`, `UPDATE <id>`,
`SUPERSEDE <id>`, or `NOOP duplicate of <id>`. The verdict is deterministic (no
model call). Show it with the candidate. Approving a `SUPERSEDE` marks the old
memory superseded; `--force` and autosave never apply a `SUPERSEDE`, they defer it.
Rule memories store the balanced text; light and strict wording is derived when
the rule is rendered unless a candidate supplies custom `LIGHT:`/`STRICT:` text.
New memories store `author_name` only (not the email) unless
`memory.include_author_email` is true.

`engram save-session` is for long sessions that produced multiple durable
memories.

`engram observe` writes sanitized raw notes into inbox only. It does not create
active memory unless routed through proposal flows later.

`engram take-control` converts existing guidance, notes, and docs into Engram
memory candidates. `--kind code|config|all` (default `docs`) also digests code
(a per-directory repo map of symbol names and imports, never bodies), config keys
and allowlisted values, and build manifests; `--objective "<text>"` names the
current objective; `--plan --json` previews sources; `--budget-tokens`,
`--max-sources`, and `--max-chars` bound the scan; `--refresh` re-proposes
`UPDATE: <id>` candidates only for memories that `engram verify --sources`
marked stale. `--from claude-auto-memory|codex-memories` reads a host memory
store (`~/.claude/projects/<project>/memory/` or `~/.codex/memories/`) read-only
and proposes candidates through the same approval gate; Engram never writes into
the host store.

`engram promote <id>` moves a working memory (see `OBJECTIVE: task` below) to
durable memory after A/B/C approval. `engram working prune [--dry-run]` deletes
expired working memories. `engram working note "<text>" [--objective <text>]
[--type knowledge|rule] [--scope workspace|global]` saves a redacted task note
(`source: note`) to the working tier after one yes/cancel approval; it writes
nothing on cancel and never updates a durable memory. SessionStart omits a note
unless `ENGRAM_SESSION_OBJECTIVE` matches its objective (otherwise it is a card).

`engram metacognize` restructures existing Engram memory through proposal-first
candidate generation.

Candidate format

When generating save-session, take-control, metacognize, or proposal-first clone
candidates, use one candidate per line:

TYPE: rule | TEXT: Always run tests before release.
TYPE: knowledge | TEXT: Release notes live in CHANGELOG.md.
TYPE: workflow | TEXT: When releasing, run tests, update changelog, then tag.

Optional fields:

- `CONTEXT: ...` explains why the memory exists or what boundary it came from
- `DEPENDS_ON: memory-id` links deeper memory to a prerequisite
- `LEVEL: advanced` marks a deeper memory layer
- `UPDATE: memory-id` asks Engram to update an existing memory
- `OBJECTIVE: task|durable` (default durable): `task` saves to the gitignored
  working tier with `valid_until` = today + `load.working_ttl_days` (default 14)
- `SCOPE: workspace|global`: overrides the command scope; under `--force` an
  out-of-scope target is deferred, not written
- `APPLIES_TO: <globs>`: up to 8 relative globs that trigger the memory when a
  matching file is read or edited
- `DIRECTIVE: <line>`: one line of at most 160 characters shown on cards

In the multi-line grammar these four field names are recognized only in
uppercase.

Examples:

TYPE: rule | TEXT: OAuth rotation follows release foundations. | DEPENDS_ON: release-foundation | LEVEL: advanced
TYPE: knowledge | TEXT: Invoice retries use exponential backoff. | UPDATE: invoice-retry-baseline
TYPE: knowledge | TEXT: Release notes live in CHANGELOG.md. | CONTEXT: Created after release planning clarified where final notes are kept.

Approval boundary

Normal writes require human review. Agents should treat Engram as approval-first
unless the human explicitly requested a force path.

Force boundaries

Use `--force` only when the human explicitly included it.

Examples:

- `engram save-session --force`
- `engram ss -f`
- `engram take-control --force`
- `engram metacognize --workspace --force`

Natural wording such as:

engram ss -f last 50 sessions

means:

engram save-session --query-level 50 --force

Only include recent human-agent chats the agent can actually access. Never
invent unavailable history.

If a force command reports related memories before writing, no file was
saved yet. Use those hints to rerun with `DEPENDS_ON` or `UPDATE` instead of
claiming a save happened.

Related memory hints

Save previews may surface:

- dependency hints
- possible duplicate warnings
- suggested restructure opportunities

These are advisory unless you are in a force restructuring flow that
explicitly pauses before writing. Do not auto-archive memory or silently rewrite
memory just because a related-memory hint exists.

Profiles, scope, and save targets

Global memory can be isolated into profiles for company, team, or personal use.

Architecture sketch:

```mermaid
flowchart TD
    Agent["Agent / CLI / MCP / Hook"] --> Query["load / search / route"]
    Query --> Rank["rank relevant memory"]
    Rank --> Workspace["workspace Markdown"]
    Rank --> Global["global/profile Markdown"]
    Workspace --> Rebuild["rebuild derived layers"]
    Global --> Rebuild
    Rebuild --> Hashes["hashes"]
    Rebuild --> Index["index"]
    Rebuild --> Graph["dependency graph"]
    Rebuild --> Vec["optional sqlite-vec (experimental, off by default)"]
    Query --> Config["optional SQLite config DB"]
```

Scope examples:

```mermaid
flowchart TB
    Normal["normal workspace load"] --> W1["workspace memory first"]
    Normal --> P1["profile/global fallback"]
    Pinned["workspace pinned profile"] --> W2["workspace memory"]
    Pinned --> P2["pinned profile"]
    Explicit["--profile different-name"] --> Off["workspace disabled for that command"]
    GlobalOnly["global-only mode"] --> G["global root only"]
    Normal --> Pinned
    Pinned --> Explicit
    Explicit --> GlobalOnly
```

Markdown memory stays source of truth. Hashes, index, graph, sqlite-vec, and
the optional SQLite config DB are support layers only.

Useful commands:

- `engram profile create <name> --global-path <path>`
- `engram profile use <name>`
- `engram profile use <name> --workspace`
- `engram profile merge <from> <to> --dry-run`

When a command uses `--profile <name>` and that profile differs from the
workspace default, workspace memory is disabled for that command to avoid
cross-profile leaks.

Save targets:

- `engram set-save-target workspace`
- `engram set-save-target global`
- `engram set-save-target both`
- `engram set-save-target status`

Per-command `--scope workspace|global|both` overrides the default target.

Agent setup and integration

This guide is intentionally safe before initialization:

engram llm

does not require `engram inject`.

To inject workspace memory and install default workspace instructions:

engram inject

To inject/initialize only global memory:

engram inject --global-only --global-path <path>

To link Engram to a host (skillset + MCP + slash + agent hooks):

- `engram link codex`
- `engram link claude`
- `engram link gemini`
- `engram link cursor`
- `engram link windsurf`
- `engram link --global opencode`
- `engram link slash`
- `engram link mcp`
- `engram link --global <target>`

`engram link <target>` installs skillset files, MCP config, slash adapters, and
agent hooks together. Use `--plan` to preview, `--force` to overwrite. `engram
unlink <target>` removes all of these together. For Cursor, workspace MCP is
written to `.cursor/mcp.json` with `type: "stdio"`, and the `sessionStart` hook
injects startup context via `additional_context`. For Windsurf/Cascade,
workspace MCP is skipped (global-only); the `pre_user_prompt` hook can
audit/preload/block but does not inject model context.

MCP config is written where each host reads it: `.mcp.json` for Claude Code,
`mcpServers` in `.gemini/settings.json` / `~/.gemini/settings.json` for Gemini,
a managed block in `~/.codex/config.toml` for Codex. Claude Code reads user-scope
servers from its own store, so global Claude linking prints
`claude mcp add --scope user engram -- engram-mcp` instead of writing a file.
MCP `engram_save` and `engram_save_session` return an `approval_token`; after the
human approves the exact candidates in chat, call `engram_commit` with that
token (single use, 30 minutes) and `approve: "all"` or candidate numbers.

Claude Code's workspace bootstrap is AGENTS.md-first: `engram link claude` writes
the managed block to `AGENTS.md` and adds a block to `CLAUDE.md` (or
`.claude/CLAUDE.md`) only when that file already exists. `engram doctor` checks
the AGENTS.md chain size against Codex's 32 KiB limit and validates generated
`SKILL.md` files against the Agent Skills spec.

The MCP server speaks MCP 2026-07-28 and the legacy handshake from one process
and returns short `instructions`. Memories are MCP resources (`engram://index`,
`engram://memory/{id}`) and one prompt, `propose`, returns the proposal protocol.
`engram_commit` carries `_meta["anthropic/requiresUserInteraction"]`, so keep the
host's per-call approval on. When the client supports elicitation,
`engram_save` and `engram_save_session` ask the human in the host's own dialog:
`accept` writes the selected candidates, `decline` revokes the proposal, and
`cancel` falls back to the `approval_token` flow. Never write after `decline`.
`engram_note` (`text`, optional `objective`, `type`, `scope`) saves a redacted
working-tier task note after the same single yes/cancel approval and returns
`{id, file, valid_until}`; cancel writes nothing. `engram promote` is the only
way a note becomes durable.

For OpenCode, `engram link --global opencode` also installs a managed local
JavaScript plugin at `~/.config/opencode/plugins/engram.js` (or the
platform/config override equivalent). The plugin uses `chat.message` to route
the current user prompt and `experimental.chat.system.transform` (an OpenCode
experimental API) to inject routed memory before each LLM request. OpenCode
must be restarted or reloaded after `link`/`unlink` because local plugin files
are loaded at startup. The plugin fails open and keeps raw routed memory only
in the running OpenCode process; Engram's disk hook cache remains hashes,
session IDs, host, cwd, and delivered memory keys only. `engram unlink --global
opencode` removes only the Engram-generated plugin; a human-authored
`engram.js` is preserved unless `--force` is explicit.

OpenCode MCP config uses a simple local entry:

```json
"engram": {
  "type": "local",
  "command": ["engram-mcp"],
  "args": [],
  "enabled": true
}
```

The local JavaScript plugin is loaded from
`~/.config/opencode/plugins/engram.js`; do not add an npm-style `plugin` entry
for that local file.

The current public Antigravity fallback is `gemini`. Hidden compatibility aliases
may still exist, but they should not be the default public recommendation.

Slash and natural language mapping

Agents may normalize human wording into canonical Engram commands.

Examples:

- `auto save` -> `save-session`
- `take control force` -> `take-control --force`
- `take control force metacognize` -> `take-control --force --metacognize`
- `restructure workspace memory force` -> `metacognize --workspace --force`
- `clone workspace memory to global` -> `clone-memory workspace global`
- `clone workspace memory to global and metacognize` -> `clone-memory workspace global --metacognize`
- `resolve conflicts and metacognize` -> `resolve-conflicts --metacognize`
- `set global memory path to <path>` -> `update-global-folder <path>`

Short aliases must preserve the same safety behavior as canonical commands.

Response style for Engram-aware agents

Prefer compact user-facing responses for read commands.

Good examples:

- `Engram loaded: 8 memories / 24 total related memories.`
- `Ran: engram verify. Result: OK workspace and global.`
- `Saved: knowledge/release-notes-location.md.`

Avoid:

- dumping full memory bodies into chat by default
- presenting hidden write behavior as if it already happened
- inventing extra approval beyond what Engram already requires

Health, maintenance, and safety

Useful maintenance commands:

- `engram verify`
- `engram repair`
- `engram rebuild-index`
- `engram graph "<topic>"`
- `engram quality-check`
- `engram health`
- `engram stats`
- `engram upgrade`
- `engram sync`

After npm package updates, normal Engram commands may run a quiet one-time
auto-upgrade for already-initialized roots. This refreshes generated help,
indexes, graph files, and eligible vector sidecars when metadata is old.

Do not assume upgrade means publish. In this repository, `npm run publish`
should stay limited to the publish action itself; tests and pack checks should be
run explicitly before publishing.

Session-end behavior

When durable rules, facts, or workflows emerged, propose:

- `engram save`
- `engram save-session`

instead of relying on private chat memory.

Keep proposals:

- concise
- objective
- durable
- reviewable

Agent checklist

1. Load Engram memory at task start.
2. Keep read responses compact unless the human asked for raw detail.
3. Reload when the task changes materially or after `Agent action:` commands.
4. Never write durable memory silently; working-tier notes are gitignored, expire, and are redacted.
5. Use force mode only when the human explicitly included it.
6. Never invent inaccessible recent chat history.
7. Use `DEPENDS_ON`, `LEVEL`, `UPDATE`, and optional `CONTEXT` when restructuring
   related memory.
8. Suggest `save` or `save-session` at the end of meaningful work.
